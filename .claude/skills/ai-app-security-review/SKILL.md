# 個人用AIアプリのセキュリティ診断

## このスキルが解こうとしている問題

この種のアプリに「セキュリティを見て」と頼むと、たいてい一般的なWebアプリ向けの
チェックリストが返ってくる。認証がない、HTTPSでない、レート制限がない、CSRF対策が、と。

しかし相手が **自分のPCのlocalhostでだけ動く、自分ひとりが使う道具** なら、
それらの多くは「欠陥」ではなく「設計どおり」である。単一ユーザーのツールに
ログイン画面を足しても、守る相手がいない。ループバック通信に盗聴者はいない。

一方で、この構成には一般的なチェックリストが拾わない、しかし現実に事故が起きている
危険がある。**持ち主自身がうっかり外に出してしまう経路** と、
**外から持ち込んだファイルの中身** である。

このスキルの仕事は、後者を漏らさず拾い、前者（当てはまらない一般論）で
レポートを水増ししないこと。所見の本数ではなく、**その1件が本当に起こりうるか**で
価値が決まる。

## 手順

### 1. まず脅威モデルを確定する

深刻度は脅威モデルなしには決まらない。同じコードでも、ひとりで使うなら問題なし、
社内に配るなら重大、ということが普通に起きる。分からないまま進めず、
コードとユーザーへの質問で次を確定させる。

- **誰が触れるか** — 自分だけか、同じ端末の他ユーザーか、LAN内の誰かか、インターネットか
- **何を食わせるか** — 自分で書いた文章だけか、他人からもらったPDFやメール本文も入るか
- **鍵は誰のものか** — 個人の無料枠か、会社の課金アカウントか
- **配る予定はあるか** — このフォルダを誰かに渡す/GitHubに上げる予定があるか
- **保存物に何が入るか** — 生成履歴に、他人に見せられない内容が入りうるか

コードから読み取れることは自分で読む（例: `.streamlit/config.toml` の `server.address` を
見れば到達範囲は分かる）。読み取れないこと（配布予定、扱う情報の機微さ）だけ質問する。
質問は最大3つまでにまとめ、それ以上は仮定を明示して進める。

### 2. 機械で決着する項目を先に片付ける

事実確認で答えが出るものは、目視より確実で速い。

```bash
python <このスキル>/scripts/scan.py <プロジェクトのパス>
# JSONで欲しいときは --json
```

このスクリプトが見るのは、秘密情報の直書き、git の追跡状況と過去のコミット、
`.gitignore` の網羅、Streamlit の待ち受け設定、起動スクリプトによる設定の上書き、
依存のバージョン固定、ローカル保存データの実体、クラウド同期フォルダの内外、
`unsafe_allow_html` の使用箇所。

出力は材料であって結論ではない。**深刻度はスクリプトが決めない**。
たとえば「.env に本物の鍵がある」は、gitに入っていなければ設計どおりで、
入っていれば重大事故になる。その判断はこの後でやる。

### 3. 4分野を読む

分野ごとに、何を見て何を根拠に判断するかを `references/` にまとめてある。
対象アプリに関係する分野だけ読めばよい。

| 分野 | 参照先 | 主に効く問い |
|---|---|---|
| APIキーと秘密情報 | `references/secrets.md` | 鍵はどこに置かれ、どこに漏れうるか |
| アップロードとプロンプト注入 | `references/uploads-and-injection.md` | 外から来た文書がモデルに何をさせうるか |
| ローカル保存データ | `references/local-data.md` | 貯まった履歴が誰の目に触れうるか |
| 公開設定と依存パッケージ | `references/exposure-and-deps.md` | 到達範囲は本当に閉じているか |

### 4. 深刻度を付ける

深刻度は「その事象がどれくらい嫌か」ではなく、
**「この脅威モデルの下で、実際にそこへ至る経路があるか」** で決める。

- **高** — 今の状態のまま普通に使い続けると、鍵か個人データが持ち主の意図しない
  相手に渡りうる。経路が既に存在する（git追跡下にある、同期フォルダにある、
  公開範囲が開いている）。
- **中** — 特定の条件が揃うと成立する。条件は現実的に起こりうる
  （他人からもらったPDFを読ませる、依存を更新する、うっかりLANに出す）。
- **低** — 今の構成では到達経路がないが、構成が1つ変わると効いてくる。
  「将来こう変えるなら、そのとき効く」と条件を明示して書く。
- **対象外** — この構成には前提が存在しない論点。指摘しないのではなく、
  「なぜ見なくてよいか」を1行で書く。書いておくと、見落としではなく
  判断した結果だと分かる。

深刻度を上げる要素: 鍵が課金アカウント / 履歴に業務情報が入る / 配布予定がある / git履歴に残っている。
深刻度を下げる要素: 単一ユーザー / localhost限定 / git管理外 / 入力が自分の文章だけ。

### 5. レポートを書く

```markdown
# セキュリティ診断レポート — <アプリ名>

- 実施日 / 対象: <パス>
- 前提とした脅威モデル: <誰が触れる・何を食わせる・配布予定・鍵の種類>
  ※ ここが違っていたら深刻度が変わるので、まず確認してほしい

## まとめ
<3行以内。いま一番危ないのは何か。今日やるなら何か。>

## 所見

### [高] <一行で言い切る見出し>
- **どこ**: `core/gemini.py:40`
- **何が起きうるか**: <具体的な筋書き。抽象語で濁さない>
- **なぜこの深刻度か**: <脅威モデルのどの前提に依存しているか>
- **どう直すか**: <最小の変更>
- **直さない場合の運用でのしのぎ方**: <コードを変えたくないとき何に気をつけるか>

## 対象外とした論点
- <論点>: <なぜこの構成では当てはまらないか>

## 機械チェックの結果
<scan.py の要約。鍵の値そのものは絶対に貼らない>
```

`直さない場合の運用でのしのぎ方` を必ず書く。個人ツールの持ち主は、
指摘のたびにコードを直したいわけではない。「触らずに済ませる方法」があるなら、
それも立派な選択肢である。

## 対象外にすべき論点（よくある水増し）

このアプリ形態では、次はそのまま書くと的外れになる。書くなら必ず条件付きで、
低として扱う。

- **認証・認可がない** — 単一ユーザーのlocalhostツールでは守る対象がない。
  書くなら「待ち受けを外に広げるなら、そのとき認証がないことが効く」という形にする。
- **HTTPSでない** — ループバック通信に中間者はいない。
- **CSRF / CORS** — Streamlit は XSRF 保護が既定で有効。既定を切っていないなら指摘しない。
  切っている場合だけ書く。
- **モデル出力によるXSS** — `st.markdown` は既定でHTMLをエスケープする。
  `unsafe_allow_html=True` を実際に使っている箇所だけが対象（`scan.py` が場所を出す）。
- **SQLインジェクション** — DBを使っていないなら存在しない。
- **レート制限がない** — 攻撃者が到達できないなら意味がない。
  ただし「自分の操作ミスで無料枠を焼く」話は別問題として書いてよい。
- **秘密の暗号化保存** — 鍵を復号できる情報が同じ端末にある以上、
  ローカル暗号化は端末を奪われた場合には効かない。効くのは「うっかり共有」に対してだけ。
  そう限定して書く。

## やらないこと

- **コードを書き換えない。** このスキルは報告までを担当する。
  直してほしいと明示されたら、レポートを出したうえで、どれを直すか確認してから着手する。
- **鍵の値をレポート・ログ・端末出力に出さない。** マスクした形（先頭4文字と文字数）
  までにする。診断のためにアプリを壊す、あるいは診断結果自体が漏洩源になるのは本末転倒。
- **推測で書かない。** 所見は必ずファイルと行番号で裏を取る。読んで確かめられなかったものは
  `[要確認]` と明示する。断定できないことを断定すると、レポート全体が信用できなくなる。
- **所見の数を目標にしない。** 該当なしなら「該当なし」と書く。
  無理に埋めた1件が、本物の1件を見えなくする。
