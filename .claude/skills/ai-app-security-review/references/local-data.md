# ローカル保存データ（生成履歴など）

生成履歴は、機能としては地味だが、機密の観点では **アプリが持つ最も濃い資産** になる。
使い込むほど、入力した業務文書・受信メール・下書きが平文で1か所に積み上がるためである。

コード上は数十行のJSONL追記でも、中身は「その人が何を書き、何を相談したか」の記録になる。
そこを踏まえて評価する。

## まず実体を見る

推測せず、実物を確認する。`scan.py` がファイルサイズと件数を出す。

- どこに保存されるか（固定パスか、設定で変わるか）
- 何が保存されるか — 出力だけか、入力（プロンプト）も含むか。
  アップロードした文書の中身が入るか
- どれだけ貯まっているか
- 削除・見直しの手段がUIにあるか

「出力だけ保存」と「入力も保存」では機微さがまるで違う。
コードを読んで、レコードに実際に入るフィールドを列挙する。

## 論点

### 平文であること

暗号化されていないこと自体を、単独で「高」にはしない。
復号できる情報が同じ端末にある以上、端末を奪われる想定では暗号化は効かない。
効くのは **フォルダごとうっかり共有した場合** に限られる。
そう限定して書くと、読む側が対策の要否を判断できる。

### 意図しない同期・バックアップ

平文であることが効いてくるのは、ここと組み合わさったとき。

- クラウド同期フォルダの中にあるか（`scan.py` の「置き場所」）
- バックアップソフトの対象になっているか
- `.gitignore` で除外されているか、**過去にコミットされていないか**

`.gitignore` に入っていても、追加する前に一度コミットしていれば履歴に残る。
履歴に業務文書が入っているなら、これは高になりうる。

### 保持期間

個人ツールに保持期間の概念がないのは普通なので、
「保持ポリシーがない」と書くだけでは意味がない。
**貯まり続けると何が困るか**（古い機密が消えない、フォルダごと渡すと全部渡る）
と対で書く。UIに削除手段があるかを確認して、なければそこを指摘する。

### 破損データの扱い

読み込み時に壊れた行を黙って飛ばす実装は、機密の問題ではない。
ただし「消えたことに気づけない」可用性の問題として、低で触れてよい。
セキュリティの所見に混ぜず、区別して書く。

### 未使用のコード経路

削除や上書きの関数が用意されているが未使用、という状態は珍しくない。
これ自体は脆弱性ではない。指摘するなら
「削除手段が実装済みだがUIから呼ばれていないので、ユーザーは履歴を消せない」
という **機能の欠落** として書く。脆弱性と混同しない。

## 直し方の引き出し

深刻度が中以下なら、コードを変えない案を先に出す。

- 保存先をクラウド同期の外に移す（設定1行、コード変更なしで済むことが多い）
- 定期的に履歴ファイルを空にする運用
- 機微な内容を扱うときだけ履歴保存を切れるトグルを足す（コード変更あり）
- フォルダを人に渡すときは `data/` を除いて渡す、をチェックリスト化する
