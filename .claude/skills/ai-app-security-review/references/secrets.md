# APIキーと秘密情報

鍵が漏れると、課金・レート枠・そのアカウントに紐づく他サービスまで影響が及ぶ。
個人ツールで最も現実的な事故はここで起きる。ただし「漏れる」の中身は、
攻撃者に破られるのではなく **持ち主が自分で外に出してしまう** ケースがほとんどである。
そのつもりで経路を洗う。

## 鍵がどこに存在しうるか

置き場所を全部数え上げてから、それぞれの外への出口を見る。

1. `.env`（`python-dotenv` が読む）
2. `.streamlit/secrets.toml`
3. 環境変数（シェルの設定ファイル、`run.bat` などの起動スクリプト）
4. 実行時のメモリ（`st.session_state`、`@st.cache_resource` のキャッシュキー）
5. ソースへの直書き（`scan.py` が検出する）
6. 上記のバックアップ、エディタの一時ファイル、シェル履歴

## 外への出口を1つずつ潰す

### git

一番事故が多い。`scan.py` が3点を見る。

- 今 `.gitignore` に入っているか
- 今 `git ls-files` で追跡されていないか
- **過去のコミットに残っていないか** — 後から `.gitignore` に足しても履歴は消えない。
  ここが残っていると、リポジトリを公開した瞬間に漏れる。深刻度は高。
  「`.gitignore` してあるから大丈夫」という思い込みを、履歴の確認で必ず裏を取る。

リモートが設定されているかも見る。ローカルだけのリポジトリと、
GitHub に push 済みのリポジトリでは、同じ状態でも緊急度がまるで違う。

### クラウド同期フォルダ

OneDrive / Dropbox / iCloud / Google Drive の下にプロジェクトがあると、
`localhost` 限定で作ったつもりでも `.env` と履歴がクラウドに上がる。
共有リンクを作った瞬間に外に出る。`scan.py` の「置き場所」を見る。

同期ツールが端末に存在するだけなら問題ない。**プロジェクトがその配下にあるか**が論点。
ここを混同して警告すると誤報になるので、パスで確認してから書く。

### 画面と配信

生成中の画面共有、スクリーンショット、録画。鍵の入力欄が
`type="password"` になっているかを見る（なっていれば表示は伏せられる）。
ブラウザのパスワードマネージャに保存される可能性にも触れてよい。

### エラーメッセージとログ

例外の文字列をそのまま画面に出している箇所があると、
SDK が投げるメッセージにリクエストURLやヘッダが含まれた場合に鍵が露出しうる。

見るべきは「未知の例外を素通しで表示している経路」。
たとえば `friendly_error()` のような変換関数の最後が
`f"生成に失敗しました: {e}"` で終わっているなら、そこが素通し口である。
既知のエラーは日本語に置き換えられていても、未知のものは生のまま出る。

深刻度は、実際にその SDK が鍵をメッセージに含めるかどうかで変わる。
確認できないなら `[要確認]` と書き、低〜中に留める。断定しない。

## 鍵の解決順序を読む

複数の供給元がある場合、優先順位に落とし穴がないかを見る。

よくある順序は「画面入力 → `.env` → `secrets.toml`」。ここで確認すること:

- 画面入力が最優先なら、共有端末で前の人の入力が残らないか（セッション単位か）
- キャッシュのキーに鍵を使っている場合（`@st.cache_resource` など）、
  そのキャッシュがプロセス全体で共有されるか。単一ユーザーなら実害はないが、
  複数人が同時に触る構成に変えた時点で他人の鍵でクライアントを引く事故になりうる。
  **今は低、構成が変わったら高** という書き方が正確。

## 直し方の引き出し

- `.env` を git 履歴から消す必要がある場合、履歴の書き換えは影響が大きい。
  まず **鍵をローテーション（無効化して再発行）** する方が速く確実。これを先に勧める。
- 起動スクリプトに鍵を直書きしている場合は `.env` に移す。
- 配布予定があるなら、鍵は同梱せず `.env.example` だけを配る形にする。
